CAPA 00 · SUPERFICIE Documentación oficial del proyecto

DIAN_DIGGIN

Plataformas 2D construido en Unity, centrado en excavar, saltar, combatir y sobrevivir capa tras capa en busca de venganza contra el gusano que arrebato un preciado tesoro del protagonista. Esto no es un Iceberg... es una madriguera. Y mientras más profundo decendamos, más secretos del proyecto iremos descubriendo y desentreñando.

Motor: Unity 6000.0.47f1 Lenguaje: C# Backend: Mono (Versión .NET que copila y ejecuta código C#) Plataforma: Windows x64 Física: Rigidbody2D

CAPA 01 · -5m

Resumen general

Pequeño contexto antes de ver código.

¿Qué habrá en el codigo?

  • Plataformas 2D con movimiento, doble salto opcional y ataque cuerpo a cuerpo.
  • Un personaje jugable llamado Dian, controlado por PlayerController.
  • Sistema de vida basado en corazones, con curación por objetos y daño por contacto enemigo.
  • Dos tipos de enemigo perseguidor (murciélago y gusano) y un jefe con salto añadido.
  • Progresión de nivel por avance secuencial de escenas, menú, pausa y créditos.

Un terreno rocoso se aproxima

A partir de aqui solo bajaremos más y más. Si bajar es tu abilidad, ¿Que eres sin tu capacidad de escabar?

CAPA 11B · -84m

Código explicado de forma sencilla

Cuatro fragmentos que resumen cómo está armado el juego por dentro, explicados en lenguaje simple. No hace falta ser experto en Unity para seguirlos.

1. Cómo se mueve Dian

Cada fotograma, el juego lee si se está presionando la flecha izquierda o derecha y usa ese número para mover al personaje. También lanza un pequeño rayo invisible hacia abajo para saber si hay suelo debajo de los pies: si lo hay, Dian puede saltar.

float movimiento = Input.GetAxis("Horizontal");
rb.velocity = new Vector2(movimiento * velocidad, rb.velocity.y);

if (enSuelo && Input.GetKeyDown(KeyCode.Space))
{
    rb.velocity = new Vector2(rb.velocity.x, fuerzaSalto);
}

2. Cómo funciona la vida del jugador

La vida vive en un solo lugar (VidaJugador). Cuando el jugador recibe daño, este script resta la vida y avisa a quien quiera enterarse mediante una "señal" (evento). El HUD de corazones está escuchando esa señal y se actualiza solo, sin que nadie tenga que decirle directamente "cambia de dibujo".

public Action<int> JugadorTomoDaño;

public void TomarDaño(int daño)
{
    vidaActual = Mathf.Clamp(vidaActual - daño, 0, vidaMaxima);
    JugadorTomoDaño?.Invoke(vidaActual); // avisa a los corazones del HUD
}

3. Cómo "piensan" los enemigos

Cada enemigo tiene solo tres estados posibles: esperando, persiguiendo y volviendo a su punto de inicio. En cada fotograma, el juego simplemente pregunta "¿en qué estado estoy ahora?" y ejecuta el comportamiento de ese estado. Es la misma idea que un semáforo: solo puede estar en rojo, amarillo o verde, nunca en dos a la vez.

switch (estadoActual)
{
    case EstadosMovimiento.Esperando:  EstadoEsperando();  break;
    case EstadosMovimiento.Siguiendo:  EstadoSiguiendo();  break;
    case EstadosMovimiento.Volviendo:  EstadoVolviendo();  break;
}

4. Un solo "director de partida" para todo el juego

GameManager se asegura de que exista una única copia de sí mismo en toda la partida (patrón llamado singleton). Así, cualquier script —sin importar en qué escena esté— puede llamar a GameManager.Instance para avisar un Game Over o pedir un reinicio, sin tener que arrastrar referencias manualmente en el Inspector.

public static GameManager Instance;

void Awake()
{
    if (Instance == null) Instance = this;
    else Destroy(gameObject); // evita copias duplicadas
}

CAPA 11C · -86m

Los 4 pilares del POO

Dian_Diggin está hecho en C#, un lenguaje orientado a objetos. Estos son los cuatro pilares de ese paradigma, cada uno con un ejemplo real tomado del proyecto.

1. Encapsulamiento

Consiste en ocultar los datos internos de un objeto y solo dejar que se modifiquen a través de métodos controlados, en vez de exponerlos libremente. En VidaJugador, la vida actual es private: nadie de afuera puede cambiarla directamente, solo puede pedirle al script que la modifique mediante TomarDaño() o CurarVida(), que se encargan de mantenerla siempre en un rango válido.

[SerializeField] private int vidaActual; // oculta, nadie la toca directo

public int GetVidaActual() => vidaActual; // solo se puede leer
public void TomarDaño(int daño) { /* la única forma de modificarla */ }

2. Abstracción

Es mostrar solo lo esencial de un objeto y esconder los detalles complicados de cómo lo hace por dentro. Cualquier script puede llamar a CurarVida(10) sin saber (ni necesitar saber) que por dentro se está usando Mathf.Clamp o disparando un evento — solo le importa el resultado.

// Desde otro script, así de simple:
vidaJugador.CurarVida(cantidadCuracion);
// Lo de adentro (el cálculo, el límite, el aviso al HUD) queda oculto

3. Herencia

Es cuando una clase toma las características de otra ya existente, para no repetir código desde cero. Todos los scripts del juego —PlayerController, VidaJugador, los enemigos, el GameManager— heredan de MonoBehaviour, la clase base de Unity. Gracias a eso, todos ganan automáticamente cosas como poder vivir en un GameObject, o recibir llamadas de Start() y Update() sin tener que programarlas desde cero.

public class PlayerController : MonoBehaviour { ... }
public class VidaJugador     : MonoBehaviour { ... }
public class GameManager     : MonoBehaviour { ... }
// las tres heredan de la misma clase base de Unity

4. Polimorfismo

Significa que un mismo método "base" puede comportarse distinto según quién lo use. Todos los scripts heredan de MonoBehaviour los mismos métodos con nombre reservado (Start(), Update()), pero cada clase redefine ese método con su propio comportamiento: en PlayerController, Update() mueve al personaje; en Creditos, Update() solo escucha si se presiona Escape. Mismo nombre de método, comportamiento distinto en cada clase.

// PlayerController.cs
void Update() { /* mueve al personaje, gestiona salto */ }

// Creditos.cs
void Update() { if (Input.GetKeyDown(KeyCode.Escape)) VolverMenu(); }

CAPA 12 · -88m

Arquitectura del proyecto

Cómo se relacionan los scripts entre sí, y qué patrones de diseño están realmente en uso.

Patrón observador para la vida del jugador

VidaJugador no conoce la existencia de la interfaz. Expone dos eventos públicos (Action<int>) y cualquier script interesado se suscribe. Esto mantiene el dato de vida desacoplado de su representación visual — un buen ejemplo de bajo acoplamiento dentro del proyecto (Principio de diseño que minimiza la interdependencia entre modulos o clases).

Duplicación entre los tres enemigos

La máquina de estados Esperando/Siguiendo/Volviendo, el giro hacia el objetivo y los Gizmos de depuración están prácticamente repetidos entre el murciélago, el gusano y el jefe. Es un caso natural para extraer una clase base común de la que los tres hereden, dejando en cada subclase solo su comportamiento distintivo (movimiento cinemático vs. por físicas, salto del jefe).

Flujo de escenas

La progresión avanza por índice de escena (buildIndex + 1), controlada por Buttons.play() y PasarNivel. Esto significa que el orden de niveles depende enteramente del orden configurado en Build Settings del proyecto Unity, no de nombres de escena explícitos.

Conclusiones

El proyecto tiene una base sólida: separación razonable de responsabilidades, un patrón observador bien aplicado para la vida del jugador, y una máquina de estados de IA reconocible y consistente entre enemigos. El código está organizado en sistemas claros —movimiento, combate, vida, IA de enemigos e interfaz— lo que facilita seguir cómo funciona el juego de principio a fin.
